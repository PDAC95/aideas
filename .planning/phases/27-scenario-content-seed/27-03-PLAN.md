scenario_templates INSERT shape (composite PK, no slug):

```sql
INSERT INTO public.scenario_templates (scenario_id, template_id, display_order)
VALUES (
    (SELECT id FROM public.scenarios WHERE slug = '<scenario-slug>'),
    (SELECT id FROM public.automation_templates WHERE slug = '<template-slug>'),
    <display_order>
)
ON CONFLICT (scenario_id, template_id) DO UPDATE SET
    display_order = EXCLUDED.display_order;
```

WHY subquery FK resolution: scenario UUIDs are auto-generated (no fixed UUIDs in seed). Slug-based subquery resolution makes the block re-emittable any time. Template UUIDs DO exist as hardcoded literals earlier in seed.sql (`ee010100-...`), but slug-based resolution is more robust and matches how the rest of seed.sql resolves cross-table refs (see automation_template_translations block lines ~1933+).

WHY ON CONFLICT DO UPDATE on scenarios: lets Patrick edit pain copy in the draft + re-run `supabase db reset --local`, with edits propagating to the DB without manual cleanup. ALSO necessary because seed.sql is RE-RUN every db reset and a plain INSERT would conflict on the slug UNIQUE constraint the second time.

WHY ON CONFLICT DO UPDATE on scenario_templates: refreshes display_order on re-run. ON CONFLICT DO NOTHING would silently ignore reorders. ALSO necessary for re-run idempotency on the composite PK.

WHY append to seed.sql (NOT a new migration): see "CRITICAL ordering constraint" in <objective>. `scenario_templates.template_id` FK references `automation_templates(id)`. `automation_templates` is populated by `supabase/seed.sql`, NOT by any migration. Supabase CLI runs migrations first, then seed.sql. If scenarios+pivot were seeded via a migration, the `(SELECT id FROM automation_templates WHERE slug = '...')` subquery would return NULL (empty table) and every pivot row would violate NOT NULL on template_id. The scenarios INSERTs themselves have no FK to automation_templates (only to functional_areas), but for symmetry + for the pivot to work, both blocks belong together in seed.sql AFTER the automation_templates inserts. functional_areas is fine in a migration because it has no FK dependency on seed-time data.

WHY dollar-quoted strings for pain_body_*: bodies contain apostrophes ("don't", "it's"). Doubling single quotes is error-prone for multi-paragraph bodies; dollar-quoting with $body_en$...$body_en$ tags (or $sb_<slug>_en$...$sb_<slug>_en$ if any body contains the literal $body_en$) survives any text.
